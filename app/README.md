# Hermes Mobile

React Native (Expo) app for Hermes. For independent mobile use, connect it to an
always-on cloud backend; the desktop computer does not need to be running.

## Setup

Use Node 24. The app needs its own build (a *development build*), not Expo Go:
background outbox delivery, Android push notifications, sharing decrypted
attachments, and on-device OpenPGP all use native modules Expo Go does not
ship. See [recovery notes](../docs/reliability.md) for validation commands and
dependency limitations.

### Build the app (once, and after any native dependency changes)

Builds run on Expo's servers (EAS), so nothing native is needed on your
computer, and iOS builds work from Windows. You need a free Expo account; iOS
also needs a paid Apple Developer account.

```bash
npm install -g eas-cli
cd app
npm install
eas login
eas init                      # links the project; writes the projectId push needs into app.json
```

Then build for your phone:

```bash
# Android: open the link it prints on the phone and install the APK
eas build --profile development --platform android

# iPhone: register the device first, then build
eas device:create
eas build --profile development --platform ios
```

Run `eas credentials` once to add push credentials: a Firebase (FCM) key for
Android. iOS push keys are created during the first iOS build.

### Develop

```bash
cd app
npx expo start --dev-client   # the installed development build connects to this
```

`eas.json` defines three profiles: `development` (with the dev client),
`preview` (an installable build that runs without your computer), and
`production` (store builds; `eas submit` uploads them). The `android/` and
`ios/` folders are generated by the build and are not committed.

**Check background delivery after a build:** turn on airplane mode, send a
message so it waits in the Outbox, close the app, then reconnect. It goes out
on the OS's schedule (15 minutes or more; longer on battery saver).

## Connecting to the cloud backend

1. Deploy the backend using [`../deploy/README.md`](../deploy/README.md).
2. In **Settings**, enter its public URL, such as `https://mail.example.com`.
3. Paste a per-device token created in the recovery settings using the server
   master token, or use the server `API_TOKEN` for initial administration.
4. Tap **Test connection**, then open Accounts.

The token is stored through Expo SecureStore (iOS Keychain / Android Keystore)
and is sent as a Bearer token on every private API request.

For local development against a backend on your LAN, start it with
`BIND_HOST=0.0.0.0` **and** an `API_TOKEN` (the server refuses to listen beyond
loopback without one), then enter `http://<lan-ip>:3001` and that token here.
The packaged desktop app's own backend is loopback-only with a per-launch token,
so the phone cannot use it.

## Screens

- **Settings** - backend URL, API token, notifications, appearance, and language
  (English or Simplified Chinese; follows the device by default)
- **Accounts** - accounts stored by the cloud backend, plus **All inboxes**
- **Folders** - every mailbox on an account, with live unread counts
- **Inbox** - list with pull-to-refresh, infinite scroll, search, and swipe
  actions (swipe right to archive, left to delete — with Undo). Long press to
  select several, then archive, delete, or mark read/unread together
- **Viewer** - full email with the earlier messages in its conversation, star,
  delete, archive, snooze, reply, attachments, and the AI summary / smart
  replies when a key is configured on the server
- **Compose** - new message, reply, encrypted local draft recovery, attachments,
  send later, undo send, and OpenPGP encryption once the address has a key
  (keys are managed in the desktop app's Settings → Encryption)
- **Local drafts** - resume or discard drafts from Settings
- **Screener** - first-time senders waiting for approval; allow or block each
  one (or a whole domain). Turn it on here or in the desktop app
- **Digest** - newsletters collected for the daily digest, grouped by sender;
  "Not a newsletter" sends a sender back to the inbox
- **Outbox**, **Rules**, **Follow-ups** - the same lists the desktop shows

Messages opened with OpenPGP show whether they were encrypted and whether the
signature checks out, above the body.

**Keeping the key on the phone.** By default the cloud backend holds your
private key and decrypts for the phone, which means the server can read your
encrypted mail while the key is unlocked. To avoid that, keep the key on the
phone instead: on the desktop, use Settings → Encryption → **Back up**, paste
that backup into the phone's Settings → **Encryption key on this phone** with
its passphrase, then delete the key from the cloud backend. From then on:

- the backend hands the phone the still-encrypted part of a message, and the
  phone decrypts and checks the signature itself;
- an encrypted reply is built and encrypted on the phone, and the backend only
  relays the finished bytes (the outbox shows its subject as `[...]`);
- a draft saved with Encrypt on stays in the phone's encrypted local storage;
- decrypted attachments open through the share sheet from a temporary file that
  is deleted afterwards;
- an encrypted reply carries the original's `In-Reply-To` and `References`
  (the phone asks the backend for them), so it threads like any other reply;
- every message the phone decrypts goes into a private search index in its
  encrypted local storage (at most 1,000 messages, 8,000 characters each), and
  searches merge its hits into the server's. Only mail opened on this phone is
  covered. Settings → Encryption key on this phone turns it off or clears it,
  and removing the last key clears it too.

The key is stored passphrase-protected in the iOS Keychain / Android Keystore
and unlocked in memory until the app closes. The phone uses OpenPGP.js 5 (it
runs without WebCrypto, which React Native lacks); the backend uses 6. Tests on
both sides open a message the other side made. The backend still sees sender,
recipients, and dates, which delivery requires. If your key requires a
passphrase and is locked, the message offers a passphrase field; the composer
asks for it when you turn Encrypt on.

Messages that could not reach the server wait in the phone's Outbox. They are
retried every 30 seconds while the app is open and, after a native rebuild, by
an OS background task while it is closed (Android WorkManager, iOS
BGTaskScheduler). The OS decides when that task runs (no more often than every
15 minutes, and often less), so it narrows the gap rather than guaranteeing
delivery. The task registers only while something is waiting.

A device token can be limited to **mail only** or **read only** when it is
created on the desktop. **Test connection** in Settings shows which one this
phone has.

## Notifications

Turn on **New mail notifications** in Settings. The app registers an Expo push
token with the backend, which then notifies this device from the same arrival
pipeline that drives the desktop's toasts — so mail arrives with the app closed
and the desktop switched off. Tapping a notification opens that exact message.
Snoozed messages notify when they wake.

Push needs a physical device; a simulator has no transport for it.

## Appearance

Light and dark, following the system by default and overridable in Settings.
The palettes are the desktop client's tokens from `frontend/src/index.css` —
keep the two in step, or the phone and the desktop stop looking like the same
product.

## Privacy

Remote images and tracking pixels are blocked until you tap **Show images**, so
opening a message does not confirm your address to the sender. The rules come
from `shared/emailPolicy.ts`, which the desktop client enforces too — the two
readers cannot drift apart.

Attachments open through a single-use link that expires in two minutes, so the
API token never reaches the system browser's history.

## Stack

Expo SDK 51, React Native 0.74, React Navigation, Zustand, axios,
react-native-render-html, react-native-gesture-handler (swipe actions), and
expo-notifications (push).
